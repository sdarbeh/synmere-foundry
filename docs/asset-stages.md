# Foundry asset stages

Foundry uses one canonical stage vocabulary across shell and avatar assets:

```ts
type FoundryAssetStage = "production" | "candidate" | "dev";
```

Stage answers one question: where is this asset in the Foundry lifecycle?

## Stages

| Stage | Meaning |
| --- | --- |
| `production` | Live verified asset. |
| `candidate` | Beta, pre-promoted asset. |
| `dev` | Work-in-progress, unverified, local, or provisional asset. |

`dev` assets must never be treated as verified, even if they load successfully
or have useful inspection data.

## Stage is not validation

Keep these concepts separate:

- `stage`: Foundry lifecycle and app visibility (`production`, `candidate`,
  `dev`);
- `validation.status`: quality/readiness result (`passed`, `needs-review`,
  `blocked`).

Example:

```json
{
  "stage": "dev",
  "validation": {
    "status": "needs-review"
  }
}
```

That record is still work-in-progress, regardless of whether it has some
validation evidence.

## Current mappings

| Asset context | Stage |
| --- | --- |
| shell production release | `production` |
| shell candidate export/review | `candidate` |
| shell dev/local experiment | `dev` |
| avatar local/test asset family | `dev` |

## Validation rules

- Release manifests must include a valid `stage`.
- Promotion records must include `version.stage`.
- Avatar asset manifests must include top-level and per-asset `stage`.
- Avatar variants inherit the lifecycle visibility of their parent asset unless
  a future manifest version explicitly adds variant-level lifecycle data.
- Shell release records and avatar asset records expose `thumbnails` arrays.
  Thumbnail entries must include a `source` so app consumers can distinguish
  real review renders from placeholders.
- Generated `@synmere/manifest` package output must include `stage` on
  app-facing release records.
- `validation.status` must be one of `passed`, `needs-review`, or `blocked`.
- `dev` assets must still include required metadata fields, but source,
  license, and author/vendor may be `unknown`.
- `candidate` and `production` assets must have known source/license metadata
  where that metadata is part of the asset record.

App consumers should use `stage` as the lifecycle signal and should not infer
asset readiness from validation wording.

## Thumbnails

Shell and avatar asset records use the same thumbnail shape:

```json
{
  "id": "preview",
  "label": "Preview",
  "kind": "preview",
  "source": "blender-render",
  "path": "assets/.../preview.png",
  "width": 1024,
  "height": 1024
}
```

`source` is required. Valid sources are:

| Source | Meaning |
| --- | --- |
| `blender-render` | Render generated by the Foundry Blender review pipeline. |
| `three-render` | Render generated by a Three.js review fallback. |
| `placeholder` | Deterministic placeholder used when real review renders are unavailable. |
| `manual` | Manually supplied thumbnail with separate review provenance. |

Empty `thumbnails: []` is valid when no render exists yet. Do not omit the
field from app-facing shell release records or avatar asset records.

## Avatar assets and variants

Avatar assets are grouped by authored asset family:

```json
{
  "id": "synmere.avatar.test-head",
  "stage": "dev",
  "thumbnails": [],
  "variants": [
    { "id": "male", "label": "Male", "thumbnails": [] },
    { "id": "female", "label": "Female", "thumbnails": [] }
  ]
}
```

Variant names are generic authored options. For the current test asset they are
`Male` and `Female`, but future variants may represent style, material, LOD,
expression, topology, rig, or other authored choices. Do not hard-code semantic
meaning from a variant id or label in product code.
